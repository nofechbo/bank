PURPOSE AND STACK

Build an AI Banking Assistant using LangGraph, LangChain, the existing Node.js/
Express API, JWT authentication, and PostgreSQL through Prisma. Use OpenRouter
with free models instead of paid OpenAI inference. PostgreSQL already exists;
no MongoDB migration is needed.

The assistant helps authenticated users understand their balance, explain recent
transactions, summarize account activity, and prepare money transfers. It also
retains general TunaBank support and banking-information abilities.

CURRENT PROJECT BASELINE

- The public support chatbot uses predefined TunaBank knowledge and recent
  messages. It has no account tools and no account access, even after login.
- SupportChat.tsx is the existing floating chat UI and stores messages in
  sessionStorage. Requests currently go to /support/chat without a JWT.
- The backend already has JWT verification and revoked-token checks, account
  balance/transaction queries, transfer handling, and PostgreSQL via Prisma.
- Login is restored from localStorage after a refresh.
- Existing chat protection includes scope checks, input/history limits, output
  limits, and an in-memory IP rate limiter. These are useful but insufficient
  as the assistant's complete security boundary.
- Transactions currently contain sender, recipient, amount, and timestamp.
  The assistant must not invent spending categories, payment purposes, merchant
  details, or other information that the database does not contain.

AGREED UI

Use one floating chat button/window with two authentication-dependent modes.
Do not add a second competing chat box. Keep the dashboard and transfer page.

Logged out:
- Existing Tuna support mode: general banking information, app navigation,
  signup/login guidance, and transfer instructions.
- Account questions invite the user to sign in.

Logged in:
- Distinct accent/color scheme and a label such as
  "Tuna · Your banking assistant" while retaining the familiar component.
- Different opening message explaining the actual available abilities, e.g.:
  "Hi! I'm your purrfect banking assistant. I can check your balance, explain
  recent transactions, and help you prepare a transfer. What can I help you with?"
- Suggested actions: "My balance", "Recent transactions", "Prepare a transfer".
- Small dismissible invitation beside the closed button, e.g.
  "Your purrfect assistant is here. Try me!" Show once after login, not on
  every page or refresh. Exact styling/copy can be refined during the UI step.
- Ordinary messages remain text; use balance cards, transaction summaries,
  and a Review transfer button when helpful.

Login starts a separate authenticated conversation. Logout restores support
mode and clears private messages and pending actions. Account switching must
never display the previous user's history. Discard stale in-flight replies
after logout/account changes.

REFRESH AND CONVERSATION STORAGE — FINAL AGREEMENT

The user stays logged in after refreshing, so the conversation must also remain.
Use sessionStorage, like the existing chatbot, for chat display history.
- Separate public support history from authenticated history.
- Scope authenticated history to the user; this key is organization, not proof
  of identity. The backend must independently authenticate all private access.
- Restore history after refresh once authentication initialization completes.
- Clear private history and pending actions on logout or account switching.
- Session storage is tab-scoped; cross-device/cross-tab history is not promised.
- Do not store JWTs, passwords, provider keys, or unnecessary account fields in
  chat history. Browser storage is accessible to page JavaScript, so render
  messages safely and avoid unsafe HTML.
- Stored messages and any submitted history are untrusted context. They are
  never authorization, proof of a tool result, or transfer confirmation.
- Fetch current balances and transaction information from the backend rather
  than treating an old displayed answer as current data.

Do not add permanent database conversation history for the first version.
LangGraph does not require permanent transcripts. For this version, reconstruct
bounded conversational context from submitted history and revalidate workflow
details. If structured server-side workflow state proves necessary, use short-
lived, user-owned state with expiry, retaining only what is needed. A displayed
draft may survive refresh but must be revalidated before use. No database
checkpointing or cross-device resume is required by the current agreement.

HOW THE ASSISTANT WORKS

1. The shared chat UI selects public support or authenticated assistant mode.
2. The private assistant endpoint verifies the JWT and token revocation.
3. The server resolves the current account from the verified identity.
4. LangGraph controls the workflow: understand the request, gather missing
   details, invoke permitted tools, and formulate a grounded response.
5. LangChain supplies the model integration and narrowly defined tools.
6. Tools validate their inputs and query authorized data through backend code.
7. OpenRouter receives only the minimal data needed to explain the result.
8. The UI displays the answer or a structured review card.

Example tools: getMyBalance, getMyRecentTransactions,
getMyTransactionSummary, and prepareTransfer.

Example workflow:
"Help me send 100" -> ask for recipient -> collect recipient -> validate
details -> display draft -> open the prefilled transfer form for user review.

The model can request tool execution; backend code decides what is permitted.
It never gets database credentials, unrestricted SQL, arbitrary API/network
access, or authority to select the authenticated account.

TRANSFER SCOPE

First version: guide and prepare only. Collect amount/recipient and open the
existing transfer form prefilled. The user reviews and submits through the
normal authenticated transfer flow. Resolve ambiguity rather than guessing a
recipient. Validate fields and funds again at submission.

Direct execution inside chat is a possible later extension, not authorized by
this plan. It would require an explicit confirmation tied to exact validated
details, duplicate-submission protection, and safe retry behavior.

The current transfer code also needs review for simultaneous requests, decimal
precision, and duplicate submissions before expanding execution capabilities.
Do not claim a transfer succeeded unless the banking backend confirms it.

ACCOUNT AND DATA SECURITY

- Verify JWT/expiry/revocation on every private request. A client login flag is
  only UI state and cannot authorize access.
- Derive the current user from the verified token, never from chat text or a
  client-provided identity. A recipient identifier cannot replace sender identity.
- Scope every query and transaction lookup to the authenticated user. Knowing
  a transaction ID or conversation ID must not allow access to another account.
- Validate tool arguments and whitelist tool capabilities. Enforce permissions
  in backend code, independently of prompts and model behavior.
- Treat user messages, browser history, and transaction text as untrusted data.
  Prompt injection cannot change permissions or enable additional tools.
- Send only necessary account fields to the model. Exclude password hashes,
  JWTs, credentials, and unrelated user records; avoid logging private payloads.
- Account data sent to OpenRouter leaves the backend. Check selected providers'
  data handling/retention settings before using real account data. Omitting
  permanent chat history does not eliminate this external data exposure.
- Safely handle expired sessions, provider failures, unavailable tools, and
  missing data without inventing balances, explanations, or successful actions.

MODEL QUOTA AND ABUSE PROTECTION — APPLIES TO BOTH CHAT MODES

Reuse useful existing guards and strengthen both public chat and private
assistant under shared application-wide quota protection.

- Enforce per-IP limits for public access and per-user plus per-IP limits for
  authenticated access. Login does not grant unlimited model usage.
- Add a shared application-wide daily budget/hard ceiling. Reserve usage
  atomically before provider calls to avoid concurrent requests overspending it.
- FINAL CLARIFICATION: Keep counters in backend memory, as in Pingwe. Share
  them between both chat routes within one backend process. No quota tables or
  conversation tables. Counters reset on restart and are not shared across
  instances; this is accepted for the project's single-backend setup.
- Cap input/history size, output tokens, model calls and tool calls per turn,
  total execution time, retries, and concurrent requests. A single assistant
  message may cause several model requests, all of which count toward limits.
- Keep OpenRouter keys only on the server; never ship them to the browser.
- Prefer free OpenRouter models for this project, but preserve the existing
  OpenAI fallback when no OpenRouter key is configured, as explicitly requested.
  No switch to OpenAI on OpenRouter errors. On exhaustion show a limit response.
- Retain scope enforcement, but adapt it to conversation context. Existing
  keyword checks alone can be bypassed by adding "bank" to an unrelated query
  and can reject valid follow-ups such as "yes", "100", or "last Tuesday".
- Reject obvious invalid/out-of-scope requests cheaply; do not rely on model
  instructions or regexes as the only protection.
- No topic filter guarantees zero wasted tokens. Server-enforced budgets bound
  consumption, while server-enforced authorization protects account access.

OPENROUTER / LANGCHAIN / LANGGRAPH

OpenRouter offers both free and paid models; using it is not automatically free.
Select a free model/router and verify tool-calling behavior before integration.
Test compatibility, bounded retries, and quota-exhaustion handling. Free model
availability and limits can change, so verify current documentation at that step.

LangChain connects the model to typed, validated tools. LangGraph coordinates
branching, follow-up questions, state, and tool results. This is the functional
difference from the current single-request knowledge chatbot, regardless of UI.

IMPLEMENTATION ORDER — ONE STEP AT A TIME

Step 1: Backend foundation and authorization
- Reuse Express, Prisma/PostgreSQL, and JWT middleware.
- Add the authenticated assistant route/service boundary alongside public chat.
- Define user-scoped data access and safe response contracts.
- Establish shared quota guards before exposing additional model usage.

Step 2: LangChain and OpenRouter tools
- Verify a free model's compatibility and add the integration.
- Implement narrow read-only balance/transaction/summary tools with validated
  inputs and server-derived account identity.
- Calculate totals in backend/database code, not model arithmetic.

Step 3: LangGraph conversation workflow
- Route general support, balance, transaction explanation, summary, and transfer
  preparation requests; collect missing details and ground answers in tool data.
- Enforce bounded calls, contextual scope checks, and safe failure behavior.
- Use bounded untrusted history for continuity; do not trust it as tool evidence.

Step 4: Shared UI with distinct authenticated mode
- For both chat modes, handle 429 responses using the Retry-After header:
  show "Try again in X seconds" with a countdown and temporarily disable sending.
  Re-enable sending when the countdown ends; never automatically resend.
- Add the assistant appearance, opening message, invitation, and suggestions.
- Send JWTs only to the private backend route and display structured results.
- Preserve history across refresh with user-separated sessionStorage.
- Clear private state on logout/account changes and handle expired sessions.

Step 5: Guided transfer preparation
- Gather and validate recipient/amount, then navigate the user to /transfer
  with those values prefilled in the existing recipient and amount fields. The
  transfer form must visibly show the draft for explicit review and its normal
  authenticated submit action remains the only way money moves.
- Carry only validated draft values through navigation; revalidate any restored
  draft in the form. Do not enable model-driven transfer execution or make a
  transfer from a chat confirmation.

Step 6: Storage/lifecycle and quota verification
- Verify refresh restoration, account separation, logout clearing, and stale
  reply handling. No permanent conversation database is planned.
- Verify shared in-memory usage counters and any necessary temporary workflow
  expiry. Quota data is separate from conversation data.

Step 7: Focused end-to-end/security validation
- Cross-user transaction/account access and forged history/tool claims.
- Invalid, expired, and revoked JWTs; refresh/logout/account-switch behavior.
- Correct balances, summaries, transaction explanations, and missing details.
- Injection and unrelated-use attempts; valid short follow-up handling.
- Per-user/IP/global limits, concurrent calls, bounded retries, provider failure.
- Transfer drafts cannot execute money movement; form submission remains
  authenticated and authoritative.

Steps may require small supporting changes in adjacent areas, but implement
only the step the user requests and report outcomes and relevant checks.
This file is a continuity reference, not authorization to implement all steps.
